# 이번 주 진행 내용

## 1. 이번 주 목표

- SSAFY용 간편 배포 플랫폼의 서비스 방향 구체화
- 백엔드 담당 기능 범위와 책임 정리
- 프론트/백엔드 배포 방식에 대한 팀 논의 기준 마련
- 사용자 입력값을 최소화하는 배포 흐름 검토
- 다음 주 역할 분담과 ERD/API 명세 작성을 위한 기반 마련

---

## 2. 이번 주 수행 내용 및 기여

### 1) 서비스 기획 방향 정리

- 사용자가 직접 AWS 설정을 알지 않아도 배포할 수 있는 구조 검토
- 사용자가 빌드 파일과 실행 정보를 입력하면 배포 URL을 제공하는 흐름 정리
- 프로젝트명, 빌드 파일, 실행 포트, Runtime, DB 사용 여부, 환경변수 등 사용자 입력 항목 후보 도출

#### 기여한 점

- 팀이 구현할 기능을 사용자 경험 관점에서 다시 정리
- “무엇을 만들 것인가”보다 “사용자가 얼마나 쉽게 배포할 수 있는가”를 기준으로 논의 방향 제시
- 이후 기능명세와 역할 분담을 진행할 수 있는 기준 마련

---

### 2) 백엔드 기능명세 초안 작성

- 백엔드가 담당할 기능 범위 초안 작성
- 사용자 인증, 프로젝트 관리, 파일 업로드, S3 저장, 배포 요청, Outbox 처리, 배포 상태 조회 기능 정리
- 배포 요청을 즉시 완료 처리하지 않고, 상태 기반으로 관리하는 비동기 처리 방향 정리
- 외부 배포 요청 실패를 고려하여 Outbox 패턴 적용 필요성 검토
- 마이페이지에서 배포 상태, URL, 실패 사유를 확인할 수 있는 구조 정리

#### 기여한 점

- 백엔드 개발 범위를 팀원이 이해할 수 있는 형태로 문서화
- 인증, 파일 업로드, 배포 요청, 상태 조회 등 백엔드 역할을 분리하여 역할 분담의 기준 제공
- 배포 요청 유실, 실패 상태 관리 등 실제 구현 시 발생할 수 있는 문제를 사전에 정리

---

### 3) 프론트 배포 방식 비교 및 논의 기준 정리

- 사용자 프론트 빌드 파일 배포 방식 비교
- K3s + NGINX 컨테이너 방식과 S3 + CloudFront 방식의 장단점 검토
- 최종적으로 사용자 프론트는 S3 + CloudFront 기반으로 제공하는 방향으로 정리
- CloudFront 사용 시 추가로 논의해야 할 항목 정리

#### 검토한 내용

- S3 + CloudFront 방식
  - 정적 파일 호스팅과 CDN 캐싱에 적합
  - HTTPS 커스텀 도메인 제공 가능
  - 프론트 컨테이너를 별도로 띄우지 않아도 됨
  - 사용자별 S3 경로 매핑, `/api/**` 백엔드 라우팅, 캐시 무효화 전략 필요

- K3s + NGINX 컨테이너 방식
  - 프론트와 백엔드를 같은 배포 단위로 관리하기 쉬움
  - Ingress 기반 라우팅 구성이 가능
  - 다만 프론트 정적 파일도 컨테이너 리소스를 사용
  - CDN 캐싱 이점은 부족함

#### 기여한 점

- 팀 내에서 혼동될 수 있는 프론트 배포 책임 범위를 정리
- S3에 파일을 저장하는 것과 S3/CloudFront를 최종 서비스 위치로 사용하는 것의 차이를 구분
- CloudFront 적용 시 사용자별 경로 매핑과 캐시 무효화가 필요하다는 리스크를 공유
- 이후 인프라/프론트/백엔드 간 책임 분리 논의의 기준 마련

---

### 4) 환경변수 입력 방식 정리

- JAR 또는 Python ZIP 파일만으로는 실행에 필요한 Secret 값을 알 수 없다는 점 확인
- JWT Secret, API Key, DB Password, OAuth Secret 등은 실행 환경에서 주입해야 한다는 점 정리
- `.env` 파일 업로드보다 key-value 1:1 입력 방식이 적절하다고 판단
- 일반 환경변수와 민감 환경변수를 구분하는 방향 검토

#### 기여한 점

- 배포 성공 여부에 직접 영향을 주는 환경변수 문제를 사전에 확인
- 사용자가 입력한 값을 항목별로 확인하고 수정할 수 있는 구조 제안
- 민감정보 암호화 저장, 재노출 금지, 로그 마스킹 등 보안 고려사항 정리
- 프론트 입력 UI와 백엔드 저장 구조를 함께 고려할 수 있는 기준 마련

## 3. 팀 기여도 평가

- 기획 단계에서 서비스 목표와 사용자 흐름을 구체화하는 데 기여
- 백엔드 기능명세 초안을 작성하여 팀이 논의할 수 있는 기준 문서 제공
- 프론트 배포 방식에 대한 기술적 선택지를 비교하여 팀 의사결정에 필요한 근거 정리
- S3 + CloudFront 사용 방향, 환경변수 입력 방식, Outbox 필요성 등 구현 전 결정해야 할 항목을 사전에 도출
- 단순 아이디어 수준의 논의를 실제 기능 범위와 개발 역할로 이어질 수 있도록 정리

---

## 4. 아쉬운 점 및 보완할 점

- 프론트 배포 방식은 S3 + CloudFront 방향으로 정리했지만, CloudFront 설정 자동화 주체는 아직 확정 필요
- 사용자별 도메인과 S3 경로 매핑 방식 추가 논의 필요
- `/api/**` 요청을 사용자 백엔드로 전달하는 라우팅 방식 추가 논의 필요
- 환경변수 저장 구조와 암호화 방식은 ERD 작성 과정에서 구체화 필요
- 기능 범위가 커질 수 있어 1차 MVP와 2차 기능 분리 필요
