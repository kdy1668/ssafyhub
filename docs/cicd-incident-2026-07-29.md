## 한 줄 요약

8GB 루트 디스크가 93%까지 차자 Jenkins가 자신의 빌드 노드를 오프라인 처리했고, 그 순간부터 모든
빌드가 큐에서 멈췄다. 그 뒤에는 **애초에 백엔드에 자동 트리거가 없었다는 사실**과 **테스트 컴파일
오류**가 숨어 있었으며, 배포 실패 시 롤백이 실행되지 않아 백엔드 컨테이너가 죽은 채 방치됐다.
그동안 프로덕션은 CI/CD 밖에서 수동으로 띄운 프로세스가 대신 서비스하고 있었다.

## 1. 증상 — 보인 것과 실제

처음 보고된 증상은 하나였다. 백엔드 코드를 `main`에 푸시해도 Jenkins에 빌드가 생기지 않는다.
조사 과정에서 증상이 층층이 갈렸다.

| 보인 것 | 실제 |
|---|---|
| 빌드가 아예 생기지 않음 | 백엔드 잡에 자동 트리거가 **하나도 없었다**. 웹훅·폴링·주기적 스캔 전부 부재 |
| 빌드가 `SUCCESS`로 끝남 | `Deploy` 스테이지가 조용히 건너뛰어짐. 컨테이너는 생성되지 않았다 |
| 프로덕션 API가 정상 응답 | 컨테이너가 아니라 SSH 세션에서 수동 기동한 `java -jar`가 서비스 중 |
| 프론트엔드는 최신처럼 보임 | 커밋 하나가 빠진 이전 번들. S3 정적 파일은 낡아도 정상 서비스처럼 보인다 |

## 2. 인과 관계

네 가지 원인이 독립적으로 존재했지만, 겉으로 드러난 순서는 디스크가 먼저였다. 각 단계가 다음
단계를 감췄기 때문에 하나를 고쳐도 증상이 그대로 남았다.

```
루트 디스크 8GB가 93% 포화 (여유 624MB)
  │   Docker 이미지·빌드 기록·워크스페이스가 한 볼륨에 누적
  ▼
Jenkins DiskSpaceMonitor 가 빌드 노드를 오프라인 처리
  │   여유 공간이 기본 임계값 1GB 아래로 떨어지면 노드를 자동으로 내린다
  ▼
모든 빌드가 "Waiting for next available executor" 에서 정지
  │   executor 개수를 늘려도 무의미 — 노드 자체가 오프라인
  ▼
배포 중 docker run 이 디스크 부족으로 실패
  │   이미 docker stop + rename 으로 구 컨테이너를 밀어낸 뒤였다
  ▼
set -eu 가 즉시 종료 → 롤백 코드에 도달하지 못함
  │   롤백이 헬스체크 실패 분기 안에만 있어 그 앞에서 죽는 경로를 놓쳤다
  ▼
백엔드 컨테이너 없음 = 프로덕션 전면 장애
      대응으로 수동 java -jar 를 기동해 서비스를 유지
```

## 4. 원인과 조치

### 트리거 — 백엔드에 자동 트리거가 존재하지 않았다

**원인.** GitLab 웹훅은 `/project/ssafyhub-frontend` 하나만 등록돼 있었고, Multibranch 잡 설정의
`<triggers/>`는 비어 있어 주기적 스캔도 없었다. 백엔드가 자동으로 빌드될 수단이 브랜치 최초
인덱싱 외에는 없었다. **원래 보고된 증상의 근본 원인이다.**

**조치.** GitLab에 백엔드용 웹훅 `/project/ssafyhub-backend`를 추가하고, Jenkinsfile에
`pollSCM('H/3 * * * *')`을 넣어 이중화했다. 웹훅이 먼저 빌드를 만들면 폴링 차례에는 새 커밋이
없어 중복 빌드는 발생하지 않는다.

**근거.**

```
GitLabWebHook#getDynamic: WebHook called with url: /project/ssafyhub-backend
병합 11:38:44 UTC  →  빌드 시작 11:39:04 UTC  (20초)
```

### 파이프라인 — `Deploy`가 조용히 건너뛰어지고 빌드는 성공으로 표시됐다

**원인.** 배포 조건이 `changeset 'backend/**'`와 `triggeredBy 'UserIdCause'`뿐이었다. 브랜치 최초
인덱싱에서는 changelog가 비어 `changeset`이 매칭되지 않고, 트리거도 `UserIdCause`가 아니라
`BranchIndexingCause`라 두 조건이 모두 빗나간다. `when`으로 스테이지를 건너뛰는 것은 실패가
아니므로 빌드는 `SUCCESS`로 끝난다.

```
Warning, empty changelog. Probably because this is the first build.
Stage "Deploy" skipped due to when conditional
Finished: SUCCESS          ← 배포되지 않았는데 성공
```

**조치.** `expression { currentBuild.changeSets.isEmpty() }`를 조건에 추가했다. "무엇이 바뀌었는지
모르겠으면 안 바뀐 것으로 단정하지 않는다"는 규칙이다. 프론트엔드 Jenkinsfile에도 같은 결함이
있어 함께 고쳤다.

### 테스트 — 컴파일 오류가 모든 배포를 막고 있었다

**원인.** `DeploymentService`에 `DevOpsDeploymentClient` 의존성이 추가됐으나
`DeploymentServiceTest`가 갱신되지 않았다. `./gradlew clean build`가 테스트 컴파일에서 실패하면
`Docker Build`와 `Deploy`가 연쇄로 건너뛰어진다.

```
error: constructor DeploymentService cannot be applied to given types;
  required: ..., DeploymentOutboxRepository, DevOpsDeploymentClient, S3ObjectVerifier, SecretEncryptor
  found:    ..., DeploymentOutboxRepository, S3ObjectVerifier, SecretEncryptor
Stage "Docker Build" skipped due to earlier failure(s)
```

**조치.** `@Mock` 선언과 생성자 인자를 추가했다. EC2의 Jenkins 컨테이너에 워크스페이스 사본을
만들어 동일한 `./gradlew build`를 실행해 `BUILD SUCCESSFUL`을 확인한 뒤 커밋했다.

### 롤백 — 배포 실패 시 서비스가 내려간 채 방치됐다

**원인.** 배포는 `docker stop` → `rename` → `docker run` 순서로 진행된다. 롤백 코드가 헬스체크
실패 분기 안에만 있었기 때문에, 그보다 앞선 `docker run` 실패나 빌드 중단은 `set -eu`로 즉시
종료되며 롤백에 도달하지 못했다. 구 컨테이너는 정지된 채 `-previous` 이름으로 남는다.

**조치.** `trap restore_previous EXIT INT TERM`으로 어느 경로로 벗어나도 직전 컨테이너를 되살리게
했다. 헬스체크를 통과해 배포가 확정된 뒤에는 `trap -`으로 해제해, 이후 이미지 정리가 실패해도
정상 컨테이너를 되돌리지 않는다.

### 리소스 — 디스크가 차면 CI 전체가 멈춘다

**원인.** 8GB 루트 볼륨에 Jenkins·Docker·백엔드 런타임이 모두 올라가 있었다. 게다가 백엔드
Jenkinsfile에는 프론트엔드에 있는 `buildDiscarder`가 빠져 빌드 기록이 무한히 쌓였다.

**조치.** EBS 볼륨을 30GB로 무중단 확장하고, `buildDiscarder(logRotator(numToKeepStr: '10'))`를
추가했다. 배포 성공 후 오래된 이미지를 정리하는 로직도 정상 동작을 확인했다 — 현재 빌드와 직전
빌드만 남는다.

### 자격증명 — AWS 액세스 키를 IAM 롤로 대체했다

**배경.** "EC2에 인스턴스 프로파일이 없으므로 자격증명을 명시적으로 주입한다"는 전제로 액세스 키를
컨테이너에 넘기고 있었다. 그 전제가 사라졌다 — `ssafyhub-backend-ec2-role`이 인스턴스에 부착됐다.

**조치.** Jenkinsfile에서 키 주입을 제거했다. SDK가 인스턴스 메타데이터에서 임시 자격증명을 받는다.

**확인한 함정.** IMDS의 `HttpPutResponseHopLimit`이 **1**이면 브리지 네트워크의 컨테이너는
메타데이터에 도달하지 못한다. 호스트에서는 되고 컨테이너에서만 깨지는 종류의 문제다.
값이 **2**임을 먼저 확인한 뒤 키를 제거했고, 제거 후 컨테이너에서 IMDS 토큰 발급을 실제로 검증했다.

### 브랜치 — 배포 대상 브랜치가 반복해서 사라졌다

**원인.** `develop`→`main` 병합 시 MR의 "Delete source branch" 옵션이 `develop`을 삭제했다.
feature 브랜치에는 맞는 규칙이지만 `develop`은 병합받는 영구 브랜치다. 하루에 두 번 삭제됐다.

**조치.** 삭제된 브랜치를 두 번 복구했다. 두 번째 복구 전에 병합커밋의 두 번째 부모를 확인해
**삭제 당시의 정확한 끝단**을 찾았다 — 로컬 브랜치는 한 커밋 뒤처져 있어서 그대로 복구했다면
CSRF 수정 커밋이 사라졌을 것이다. 근본 대응으로는 배포 대상을 `main` 하나로 고정해, 사라질 수
있는 브랜치에 파이프라인이 의존하지 않게 했다.

### 설정 — 연동 주소의 끝 슬래시

**원인.** `DEVOPS_WAS_BASE_URL`이 `.../8081/`로 끝나 있었다. `RestClient`가 `/api/deployments`를
덧붙이면서 경로가 이중 슬래시가 될 수 있고, 대상 서버는 이를 거부한다. 배포 요청은 실패 시 재시도
없이 영구 `FAILED`가 되므로 조용히 유실될 수 있는 경로였다.

```
/api/deployments    →  405  (엔드포인트 존재, GET 불허 — 정상)
//api/deployments   →  404  (이중 슬래시는 매칭되지 않음)
```

**조치.** Jenkins 크리덴셜에서 끝 슬래시를 제거하고 재배포로 반영했다.

### 운영 — 프로덕션이 CI/CD 밖에서 돌고 있었다

**상태.** 배포 실패 대응으로 기동한 수동 `java -jar` 프로세스가 프로덕션을 서비스하고 있었다.
SSH 세션 스코프에 묶여 있어 재부팅하면 사라지고, 죽어도 자동 재시작되지 않는 상태였다.

**조치.** 수정을 병합한 뒤 프로세스를 정지하고 Jenkins 파이프라인 배포로 컷오버했다. 현재는
컨테이너가 8080을 점유하며, 다음 배포부터는 파이프라인이 `stop`→`rename`→`run`으로 스스로 포트를
넘긴다.

**남겨둔 것.** `app.jar`과 SSM Parameter Store에서 설정을 읽는 `start-backend.sh`는 롤백 수단으로
보존했다.

## 5. 현재 구조

| 잡 | 웹훅 | 폴링 | 배포 대상 | 산출물 |
|---|---|---|---|---|
| 백엔드 | 있음 | 3분 | `main` | EC2 Docker 컨테이너, 8080 |
| 프론트엔드 | 있음 | 없음 | `main` | S3 `ssafyhub-frontend` + CloudFront |

배포 조건은 `branch 'main'`이 AND로 걸려 있어 다른 브랜치는 배포되지 않는다. 모노레포이므로 각
잡은 자기 디렉터리 변경에만 반응한다 — `backend/`만 바꾼 푸시에서 프론트엔드 `Deploy`가 실제로
건너뛰어지는 것을 확인했다.

두 S3 버킷의 역할이 다른 점도 정리해둔다.

| 버킷 | 용도 | 접근 주체 |
|---|---|---|
| `ssafyhub-frontend` | 우리 프로젝트의 Vue 빌드 산출물 | Jenkins 프론트엔드 잡 |
| `ssafyhub-artifacts` | 서비스 사용자가 올리는 배포 파일 | 백엔드 앱 (presigned URL) |

인스턴스 롤은 `ssafyhub-artifacts`에만 권한을 갖는다.

| 우선순위 | 항목 |
|---|---|
| 높음 | **프론트엔드 잡의 브랜치 필터를 `main`으로 제한.** Multibranch는 각 브랜치의 Jenkinsfile을 읽어 실행한다. 지금은 feature 브랜치가 자기 Jenkinsfile을 수정해 프로덕션에 배포할 수 있고, 브랜치 필터가 유일한 구조적 차단이다 |
| 높음 | **노출된 프로덕션 시크릿 교체 검토.** DB 비밀번호, 암호화 키, AWS 액세스 키가 진단 과정에서 평문으로 드러났다 |
| 중간 | **Outbox 재시도 로직 부재.** 전송 실패 시 `FAILED`로 종결되고 재시도가 없다. 처리 중 프로세스가 죽으면 `PROCESSING`에서 영구 정체되며 복구 스윕도 없다 |
| 중간 | **Mattermost 알림 문구가 배포 여부를 구분하지 않음.** `Deploy`를 건너뛴 빌드도 "빌드와 배포가 성공"이라고 알린다 |
| 중간 | **Jenkins 9090 포트 외부 노출.** `/project` 엔드포인트 인증이 꺼져 있어 URL을 아는 누구나 빌드를 트리거할 수 있다. 보안그룹으로 제한하는 것이 간단하고 확실하다 |
| 낮음 | 프론트엔드 Jenkinsfile에 `pollSCM` 추가 — 현재 웹훅이 유일한 트리거 |
| 낮음 | 미구현 엔드포인트 두 개 — 관리자 배포 목록, 배포 리소스 조회 |
| 낮음 | `develop` 보호 브랜치 설정과 MR 옵션 정리 (팀 합의 사항) |

## 8. 교훈

- **성공은 성공했다는 뜻이 아니다.** `when`으로 건너뛴 스테이지는 빌드를 `SUCCESS`로 남긴다.
  배포 여부는 빌드 결과가 아니라 컨테이너·객체 같은 **결과물**로 확인해야 한다.
  이번 진단을 가장 오래 지연시킨 요인이다.
- **트리거 수단은 이중화한다.** 원래 증상의 근본 원인은 "트리거가 하나뿐이었는데 그것이 없었던
  것"이다. 웹훅과 폴링을 함께 두면 한쪽이 끊겨도 배포는 이어진다.
- **롤백은 실패 분기가 아니라 전 경로에 걸어야 한다.** 스크립트가 어디서 죽든 서비스가 내려간 채
  남지 않도록 `trap`을 쓴다.
- **모른다는 상태를 안 바뀐 상태로 단정하지 않는다.** changelog가 비었을 때 "변경 없음"으로
  처리하면 배포가 조용히 사라진다.
- **호스트에서 되는 것이 컨테이너에서도 된다고 가정하지 않는다.** `localhost`와 IMDS hop limit
  모두 이 경계에서 갈린다.
- **CI를 서비스와 같은 디스크에 두면 디스크 하나가 배포 능력을 인질로 잡는다.** 여유 공간은 용량이
  아니라 가용성 문제다.
